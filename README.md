# Гуляш

Каркас сервиса поиска поставщиков для food-бизнеса. Сейчас реализован спринт 01: React-приложение, ASP.NET Core API, PostgreSQL, модель фактов и источников, EF Core-миграции и проверка готовности.

## Запуск всего приложения

Нужны Docker Compose и доступ к Docker Engine.

1. Скопируйте `.env.example` в `.env` и задайте `POSTGRES_PASSWORD` случайным паролем для локальной базы.
2. Выполните `docker compose up --build`.
3. Откройте `http://localhost:3000`. API готов, когда `http://localhost:8080/api/v1/health/ready` отвечает `200`.
4. Фактическая OpenAPI-схема доступна на `http://localhost:8080/openapi/v1.json`.

PostgreSQL хранит данные в именованном volume `postgres_data`. API применяет неприменённые EF Core-миграции при старте; история миграций хранится в `__EFMigrationsHistory`, поэтому повторный запуск не создаёт схему заново. Для небольшого прототипа миграции запускаются одним экземпляром приложения; для окружения с несколькими репликами используйте отдельный шаг миграции перед выпуском.

Файл `.env` игнорируется Git. Значения `.env.example` — только placeholders. Пароли, мастер-ключ и ключи ИИ-провайдеров не входят в репозиторий. Сессия и CSRF будут реализованы в спринте 02/06; интеграция ИИ и API каталога добавляются последующими спринтами.

## Локальная разработка

Для frontend: из `frontend` выполните `npm ci`, затем `npm run dev`. Vite проксирует `/api` и `/openapi` на `http://localhost:8080`.

Для backend нужна доступная PostgreSQL. Перед `dotnet run --project backend/Api/Goulash.Api.csproj` задайте переменные `Database__Host`, `Database__Port`, `Database__Name`, `Database__User` и `Database__Password`. API автоматически применяет миграции при старте.

Командный инструмент EF Core закреплён как локальный tool в `backend/.config/dotnet-tools.json`. Для новой миграции восстановите его через `dotnet tool restore`, затем из `backend` выполните `dotnet tool run dotnet-ef migrations add <MigrationName> --project Infrastructure/Goulash.Infrastructure.csproj --startup-project Api/Goulash.Api.csproj --output-dir Persistence/Migrations`.

## Структура

- `backend/Api` — HTTP-маршруты, ошибки и OpenAPI.
- `backend/Application` — правила идентификации поставщиков и сценарии приложения.
- `backend/Domain` — сущности и правила происхождения фактов.
- `backend/Infrastructure` — PostgreSQL, EF Core, транзакции и миграции.
- `frontend/src/pages` — страницы и маршруты SPA.
- `frontend/src/features` — папка для функциональных модулей следующих спринтов.
- `frontend/src/shared` — общий API-клиент, каркас приложения и UI.

## Данные и происхождение

Внешние сведения представлены фактами `official` или `external`; `missing` вычисляется при отсутствии текущего факта. Каждый сохранённый факт связан с одной или несколькими конкретными страницами и непустыми выдержками. Текущий факт названия связан с `suppliers.current_name_fact_id`; отложенные ограничения проверяют готовую транзакцию и отклоняют поставщика без подтверждённого названия. Все привязанные к факту источники должны принадлежать тому же поставщику. Несогласующиеся наблюдения остаются альтернативными фактами. Товары и цены хранятся как индексируемые проекции фактов в тех же транзакциях записи.

Уникальный индекс официального домена защищает от его конкурентного дублирования. Для кандидатов с совпадающими нормализованным названием и регионом `SupplierIdentityLock` даёт транзакционную PostgreSQL-блокировку. `SupplierDataTransaction` сохраняет факты, источники и индексируемые проекции в одной транзакции.

## API ошибки и логи

Ошибки отдаются как `application/problem+json` с `code` и `traceId`. Готовность проверяет PostgreSQL отдельным запросом. Логи содержат событие и trace ID, но не тело запросов, содержимое ответов модели, заметки, cookie, ключи или исключения драйвера с деталями подключения.
