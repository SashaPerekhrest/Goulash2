# Техническое задание: поиск поставщиков для food-направления

## 1. Назначение и границы первой версии

Веб-сервис помогает находить поставщиков ингредиентов, готовой продукции, упаковки и других товаров для пищевого бизнеса, сохранять найденные компании и выбирать, с кем связаться. Целевая аудитория прототипа — один пользователь или небольшая команда с общей базой. Для публичной демонстрации доступ к приложению защищается учётной записью администратора; роли, совместная работа и разграничение избранного по пользователям в первую версию не входят.

По исходному заданию сервис должен искать по категории и региону, показывать контакты и источники, помогать сравнивать условия. Дополнительные данные — минимальный заказ, цена, сертификаты, доставка, регионы работы и заметки — включены в первую версию, если они доступны в источниках.

## 2. Основной сценарий

1. Пользователь задаёт текстовый запрос и/или фильтры на странице «Найти поставщиков».
2. Backend отправляет структурированный запрос адаптеру ИИ-провайдера с веб-поиском. За один запуск сохраняется и возвращается не более пяти подходящих поставщиков.
3. Backend проверяет структуру ответа, ссылки и дубли; сохраняет результаты в PostgreSQL.
4. Страница показывает карточки найденных компаний с краткой информацией и признаками достоверности.
5. Пользователь открывает карточку, изучает все сведения, источники, добавляет компанию в избранное и при необходимости оставляет заметку.
6. Страница «База поставщиков» сразу показывает все ранее сохранённые компании и выполняет поиск локально, без ИИ.

## 3. Страницы и поведение

### 3.1. Поиск новых поставщиков

Начальное состояние: только поле запроса, конструктор фильтров и подсказка; карточек нет. Поле запроса допускает свободный текст. Фильтры: город/регион, категория или вид товара, диапазон цены, максимальный срок доставки, минимальный/максимальный объём заказа при наличии сопоставимых единиц. Достаточно текста или одного фильтра для запуска поиска; пустой запрос без фильтров запрещён.

Изменения запускают поиск после задержки 700 мс. Кнопка «Найти» запускает его сразу. Новый ввод отменяет ожидание предыдущего запуска; одновременно от одной страницы отправляется не более одного запроса. Во время выполнения видны индикатор и параметры запущенного поиска. Повторение того же поиска доступно явной кнопкой.

Возвращается не более пяти компаний. Карточка содержит название, город, товары, краткую цену/условия доставки при наличии, сайт или контакт, отметку избранного и общий признак наличия неподтверждённых сведений. Статус и источник каждого отдельного поля доступны в деталях. Предусмотрены состояния «ничего не найдено», «провайдер не настроен», «ошибка/тайм-аут», «часть данных не получена». История поисковых запросов не является обязательной для первой версии.

Фильтр по числовому условию применяется только к сопоставимому значению с источником. При неизвестной цене, сроке или минимальном заказе компания не считается подходящей под заданный предел. Значение со стороннего сайта может участвовать в подборе, но показывается как неподтверждённое. По умолчанию ценовой фильтр учитывает только точные цены. Пользователь может явно включить примерные цены; в результатах такие значения всегда помечаются «ориентировочно». Валюта и единица измерения не преобразуются автоматически.

### 3.2. База поставщиков

Сразу после открытия отображается первая страница записей. Доступны текстовый поиск по названию/товарам, те же применимые фильтры, фильтр «Избранное», сортировка по дате добавления и названию, переключение избранного и переход в детали. Единообразные карточки с товарами, ценой и доставкой помогают сравнить найденные варианты; отдельный экран сравнения в первую версию не входит. Запросы выполняются только к внутренней базе. Пагинация серверная, размер страницы по умолчанию 20, допустимо 10–50.

### 3.3. Детали поставщика

Отображаются название, описание, товары, адрес, регионы работы, контакты, сайт, цены с валютой и единицей измерения, минимальный заказ, сроки и условия доставки, сертификаты/документы, фотографии по ссылкам, источники и дата обновления. У названия и каждого другого полученного извне поля показываются значение, статус достоверности и подтверждающий источник либо состояние «Нет данных». Избранное и заметка общие для пользователей общей базы; заметку можно изменить.

Каждое полученное из внешних источников поле имеет одно из трёх состояний:

| Состояние | Условие | Текст в интерфейсе |
| --- | --- | --- |
| `official` | Значение найдено на подтверждённом официальном сайте поставщика | «Подтверждено официальным источником» |
| `external` | Значение найдено только на стороннем сайте | «Не подтверждённая информация» |
| `missing` | Надёжного значения не найдено | «Нет данных» |

Рядом с заполненным полем доступны ссылка на конкретный источник и дата получения. Ссылка на сайт компании сама по себе не подтверждает остальные поля. Если официальная и сторонняя публикации расходятся, приоритет у официальной, а расхождение видно в списке источников. При отсутствии официального сайта сведения из иных источников сохраняются со статусом `external`. Не следует показывать пустые изображения или подставлять придуманные контакты.

### 3.4. Настройки интеграции

Пользователь выбирает одного из поддерживаемых адаптеров провайдера, указывает модель и API-ключ, сохраняет настройки и может проверить подключение. Интерфейс показывает, настроен ли ключ, но не возвращает его значение после сохранения. Предусмотрены замена и удаление ключа. Поиск недоступен, если провайдер не настроен или не поддерживает получение актуальных источников.

## 4. Получение и качество данных

Backend преобразует запрос в структурированные условия и инструкцию для модели: искать реальные компании, возвращать максимум пять записей, не заполнять неизвестные значения догадками, указывать URL источников для каждого факта, соблюдать заданную JSON-схему. Провайдер должен иметь доступ к актуальным веб-источникам. Ответ обычной модели без веб-поиска не считается основанием для сохранения поставщиков.

Backend проверяет JSON-схему, обязательные название и хотя бы один URL источника, корректность URL и допустимые размеры полей. Максимум пять результатов обеспечивается на сервере независимо от ответа модели. Факт привязывается к конкретной странице и извлечённому фрагменту её содержания, предоставленному инструментом веб-поиска. Если модель сообщает значение без такого подтверждения, оно не сохраняется. Официальный домен определяется по сайту компании и проверяется сервером; объявление модели «официальный» само по себе не принимается. Источники сохраняются вместе с датой сбора. Невалидные записи пропускаются, а ответ сообщает число пропущенных записей.

Дубли ищутся сначала по нормализованному домену официального сайта. Если новый подтверждённый домен не найден в базе, проверяется запись без домена с тем же нормализованным названием и регионом; при отсутствии противоречащих идентифицирующих признаков её дополняют доменом. Для записи без домена сравниваются название и регион существующих записей, а неоднозначные совпадения не сливаются автоматически. Повторный поиск обновляет факты и источники, но сохраняет избранное и заметку. Противоречащие факты не перезаписываются молча: выбранное актуальное значение и альтернативные наблюдения доступны в деталях. Фотографии хранятся как URL внешних источников; отсутствие фотографии допустимо.

Сервис показывает собранную информацию для предварительного выбора, а не гарантирует актуальность коммерческих условий. Пользователь видит дату получения сведений и может перейти к источнику перед обращением к компании.

## 5. Технологии и ограничения

- Backend: ASP.NET Core Web API, EF Core, PostgreSQL.
- Frontend: React с TypeScript.
- Развёртывание: Docker Compose с контейнерами frontend, backend, PostgreSQL.
- API-ключи и пароль администратора не включаются в репозиторий. Ключ хранится на сервере в зашифрованном виде; мастер-ключ передаётся через переменную окружения/секрет окружения.
- Все внешние URL при открытии проверяются на допустимую схему `https`/`http`; сервер не загружает фотографии по произвольным адресам.
- Внешние обращения имеют тайм-аут, ограничение размера ответа и диагностируемые ошибки. Секреты и полный текст ответа провайдера не пишутся в логи.

Архитектурные решения и схема данных описаны в [architecture.md](architecture.md), HTTP-контракты — в [api-contracts.md](api-contracts.md), последовательности работы — в [application-flow.md](application-flow.md).

## 6. Критерии приёмки

1. Поиск с текстом и/или фильтром даёт не более пяти валидных поставщиков; пустой поиск не запускается.
2. Результаты сохраняются, повторный поиск не создаёт дубликаты и не стирает избранное/заметки.
3. База открывается с сохранёнными данными, ищет и фильтрует без обращения к ИИ, поддерживает пагинацию.
4. В деталях по каждому полю видны значение и источник либо «Нет данных»; сторонние сведения явно помечены «Не подтверждённая информация».
5. Ключ настраивается через UI, не раскрывается в ответах API и не попадает в клиентскую сборку.
6. Приложение запускается через Docker Compose по README; миграции применяются при развёртывании.
7. При ошибке провайдера интерфейс показывает понятное сообщение; частичный невалидный ответ не повреждает уже сохранённые данные.
