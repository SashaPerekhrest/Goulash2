# Спринт 04. Двухэтапный поиск и сохранение поставщиков

## Цель

Реализовать фоновый поиск из двух простых этапов: получить первичный список поставщиков с учётом фильтров и для каждого поставщика сформировать полный JSON-профиль, который переносится в сущности и сохраняется.

## Алгоритм

1. API проверяет запрос и числовой формат фильтров, создаёт задание `queued` и отвечает `202` с `discoveryId`.
2. Первый запрос к модели получает исходный текст и все фильтры как дополнительные критерии поиска. Модель возвращает до 20 лидов: название и URL сайта.
3. Backend открывает сайт каждого лида, собирает до восьми подходящих публичных страниц, после чего отправляет отдельный запрос веб-поиска для этого поставщика.
4. Второй запрос возвращает структурированный JSON со всеми доступными сведениями о компании и товарах.
5. Backend разбирает этот JSON и переводит поля в факты и поисковые проекции. Отдельной проверки фактов и повторной фильтрации по запросу нет.
6. Успешные профили сохраняются; ошибка профильного запроса считается в `failedProfileCount` и не прекращает обработку остальных.
7. Существующий поставщик обновляется по домену или нормализованному названию. Избранное и заметка сохраняются.

## Технические требования

- Пустой запрос разрешён, если задан хотя бы один содержательный фильтр. Фильтры валидируются по формату; фактическое соответствие поставщиков оценивается моделью в первом поиске.
- Первый этап ограничен 20 лидами. Для профилей ограничено число параллельных вызовов; отсутствие необязательных полей не отбрасывает профиль.
- Структура JSON проверяется, чтобы результат можно было преобразовать в сущности. Факт-матчер, цитатная проверка и бизнес-валидация полей не участвуют.
- Публичные HTTP(S)-URL сайта проверяются до загрузки. Обход ограничен восемью страницами, 35 секундами на сайт и размером ответа.
- Фильтры не применяются к JSON второго этапа. Цена, валюта и единицы нормализуются только для хранения и последующего локального поиска в каталоге.
- Ссылки страниц и доступные цитаты сохраняются на уровне поставщика как справочная информация. Значения фактов имеют статус `aiGenerated`.
- `GET /discoveries/{id}` возвращает этап и прогресс, `acceptedCount`, `failedProfileCount`, итоговые карточки и outcome `no_candidates | complete | partial | profiles_failed`.

## Проверяемый результат

- Первый этап получает фильтры, возвращает список и запускает один запрос обогащения на каждый лид.
- Профиль сохраняется, даже если в нём есть только название или часть полей отсутствует.
- Неудача одного профильного запроса не мешает сохранять остальные профили.
- При пустом первичном списке возвращается пустой результат без дополнительного вызова.
- Повторное обнаружение обновляет запись без потери избранного и заметки.

## Передача в следующий спринт

Поиск возвращает сохранённые карточки; каталог и детали читают их из PostgreSQL. Контракт поиска описан в [разделе 4 API](../api-contracts.md).

## Реализация в проекте

`POST /api/v1/discoveries` создаёт фоновое задание. `DiscoveryBackgroundWorker` восстанавливает незавершённые задания после перезапуска, `SupplierDiscoveryService` выполняет два этапа, `SupplierSiteResearcher` читает сайт, а `DiscoveryPersistence` транзакционно записывает профиль, проекции и итог задания. Миграция расширяет допустимый статус факта до `ai_generated` и снимает ограничения, требовавшие источник у каждого значения.
