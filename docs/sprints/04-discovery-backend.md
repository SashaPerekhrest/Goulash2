# Спринт 04. Серверный поиск и сохранение поставщиков

## Цель

Реализовать `POST /api/v1/discoveries`: запрос с текстом или фильтрами вызывает провайдера, проверяет условия и сохраняет максимум пять пригодных компаний.

## Работы

1. Ввести DTO запроса и серверную валидацию: текст не длиннее 500 символов; нужен текст или хотя бы один содержательный фильтр (один `includeApproximatePrices` не считается условием); числовые границы неотрицательны и упорядочены. Валюта и единица обязательны при фильтре цены, единицы нижней и верхней границ минимального заказа совпадают.
2. Передавать провайдеру город, регион, категорию, товар, цену, срок доставки и границы минимального заказа. Город и регион соотносить с местом работы либо подтверждённой зоной доставки.
3. Применять фильтры на сервере после проверки источников. Неизвестные и несопоставимые числовые значения не проходят заданное числовое условие. Валюты и единицы автоматически не конвертировать.
4. По умолчанию учитывать в ценовом фильтре только точные цены. При `includeApproximatePrices=true` разрешить примерные; диапазон примерной цены должен пересекаться с заданным диапазоном, а карточка явно помечать цену «ориентировочно».
5. Искать дубликат сначала по нормализованному официальному домену. Если новый домен не найден, проверять запись без домена по названию и региону; при входящей записи без домена проверять название и регион среди всех записей. Не сливать неоднозначные совпадения или записи с противоречащими идентифицирующими признаками. Разрешать конкурирующие сохранения без появления дублей.
6. В одной транзакции создавать или обновлять поставщика, текущие и альтернативные факты, источники, поисковые поля и запись `discovery_runs`. При повторном обнаружении сохранять `isFavorite` и `note`.
7. Формировать ответ с `discoveryId`, максимум пятью карточками, `acceptedCount`, `rejectedCount`, `updatedExistingCount`. Отклонённые записи и записи вне условий поиска считать в `rejectedCount`. Данные карточек брать из сохранённых записей.
8. Возвращать `PROVIDER_NOT_CONFIGURED`, `PROVIDER_UNAVAILABLE`, `PROVIDER_TIMEOUT`, `PROVIDER_INVALID_RESPONSE` и ошибки валидации по контракту. Если валидных записей нет, возвращать пустой `items` без создания поставщиков.

## Проверяемый результат

- Пустой запрос с пустыми фильтрами получает `400`; запрос с одним содержательным фильтром допустим.
- В ответе не более пяти карточек после валидации и фильтрации. Неверная оболочка ответа, тайм-аут и отказ провайдера не меняют сведения о поставщиках; неудачный запуск может фиксироваться отдельно.
- Валидные записи частичного ответа сохраняются, невалидные пропускаются и отражаются в счётчиках.
- Повторный запрос обновляет факты и источники без дубля поставщика и без потери избранного или заметки.
- Фильтры по цене, сроку и заказу не пропускают неизвестные или несопоставимые значения; режим примерных цен работает только при явном включении.

## Передача в следующий спринт

В PostgreSQL есть нормализованные поставщики и факты, пригодные для локальных запросов базы и подробного отображения. Контракт ответа соответствует [разделу 4 API](../api-contracts.md).

## Реализация в проекте

- `POST /api/v1/discoveries` принимает DTO поиска. Сервер ограничивает текст 500 символами, проверяет содержательные фильтры, неотрицательные числовые границы, порядок диапазонов, валюту/единицу цены и совпадение единиц минимального заказа. Денежные границы принимаются десятичными строками; для совместимости допускаются и JSON-числа.
- Настроенный `ISupplierDiscoveryProvider` получает текст, структурированные фильтры и лимит 5. Ответ провайдера повторно проверяется по безопасным URL, фрагментам и допустимым полям до локальной фильтрации.
- Локальный фильтр сравнивает город/регион с фактами места работы и подтверждённой зоны доставки, категорию и товар — с фактами каталога, срок — с сопоставимым известным числом, цену — с пересечением диапазонов при той же валюте и единице, а минимальный заказ — с тем же значением единицы. Приблизительные цены без явного включения не подходят; неизвестные границы не считаются совпадением.
- Дедупликация сначала ищет точный нормализованный официальный домен. Затем используются только предусмотренные контрактом совпадения названия и региона. Неоднозначные совпадения и записи с одновременно расходящимися названием и регионом отклоняются. PostgreSQL advisory transaction locks сериализуют конкурирующие сохранения по домену и паре названия/региона.
- Поставщик, исходное и нормализованное значение факта, альтернативы, версии фрагментов источника, проекции товаров/цен и успешный `discovery_runs` сохраняются в одной транзакции. Миграции сохраняют прежние уникальные URL, но разрешают хранить новую версию фрагмента той же страницы. Повторное обнаружение не изменяет избранное и заметку. Ответные карточки читаются из сохранённых фактов; при ошибках провайдера отдельно сохраняется только неудачный запуск.
- В контракте API закреплены значения `acceptedCount`, `updatedExistingCount` и коды ошибок провайдера. Адаптер Perplexity дополнительно получает правило сверять город/регион с местом работы или зоной доставки и использовать общий `itemKey` для фактов одного товара.
